# ORM vs Stored Procedure
"데이터 처리 로직은 ORM과 SP 중 뭘 사용해서 구현하는게 좋을까?"

## ORM (Object-Relational Mapping)
애플리케이션(Java / Python) 코드로 데이터를 조작. DB는 저장소 역할만.
> 탄생 배경 : 객체와 테이블 간의 불일치 해결

## Stored Procedure (SP)
- 핵심 : 데이터 옆에서 처리
- DB 내부에 로직(함수)을 저장해두고 DB엔진이 직접 실행

> 단순 쿼리를 넘어 조건문(IF), 반복문(LOOP) 등 복잡한 데이터 로직을 DB 내에서 완결

## 로직 위치 
- ORM : 데이터를 가져와서 앱에서 가공 
- SP : 명령만 내리고 DB가 가공

## 한눈에 비교 (Summary)

### ORM
- 로직 위치 : Application Server
- 장점 : 생산성, 유지보수, DB 독립성
- 단점 : 복잡한 쿼리 비효율 (N+1)
- 변경시 : 코드 배포 필요 (CI/CD)

### Stored Procedure
- 로직 위치 : Database Server
- 장점 : 성능 최적화, 네트워크 절약
- 단점 : 디버깅 어려움, DB 종속성
- 변경 시 : DB 스크립트 수정 (즉시 반영)

## The Great Debate (단점)
### ORM 아킬레스건
- N + 1 문제 : 쿼리 한방이면 될 걸 수백번 날려서 DB 죽임
- 복잡한 쿼리 : 통계/집계 쿼리는 SQL을 직접 짜는게 훨씬 빠르고 쉬움

### SP의 치명적 단점
- Vendor Lock-in : 오라클 쓰다가 MySQL로 못 넘어감 (문법 다름)
- 버전 관리 지옥 : Git으로 관리하기 힘들고, 배포 프로세스가 꼬임
- DB 부하: 비싼 DB 자원을 로직 계산에 씀 (Scale-out 어려움)

## ORM 추천
- 일반적인 CRUD 비즈니스 로직
- 빠른 개발과 유지보수성이 중요할 때
- DB가 변경될 가능성이 있을 때
- 팀원들이 SQL보다 코드에 익숙할 때

## SP 추천
- 수백만 건의 대량 배치(Batch) 작업
- 복잡한 통계/집계 처리
- 네트워크 왕복 비용을 줄요야 할 때
- 절대적인 데이터 무결성이 필요할 때

## 정리
1. 기본적으로는 ORM을 사용하여 비즈니스 로직을 애플리케이션 계층에서 관리하고, 유지보수성과 생산성을 높이는 것을 선호한다.
2. 하지만 대용량 데이터의 배치 처리나 복잡한 통계 쿼리처럼 성능이 우선인 경우에는 Stored Produre이나 직접 SQL을 사용하는 하이브리드를 채택하겠다.

## 꼬꼬무

### Q1. ORM의 N + 1 문제는 어떻게 해결하는가?
- 원인 : 연관 엔티티를 지연 로딩(Lazy)으로 가져오면서, 부모 1번 조회 + 자식 N번 조회가 발생
- Fetch Join : JPQL `join fetch`로 연관 엔티티를 한 번의 쿼리로 함께 조회 (가장 기본 해결책)
- @EntityGraph : Spring Data JPA에서 메서드에 어노테이션으로 함께 가져올 연관 관계 지정
- Batch Size : `@BatchSize` / `default_batch_fetch_size` 설정으로 자식을 `IN (...)` 쿼리로 묶어서 조회 (N번 -> 1~2번)
- DTO 직접 조회 : 화면에 필요한 컬럼만 select 하는 쿼리를 QueryDSL 등으로 직접 작성
- 주의 : 컬렉션 Fetch Join + 페이징은 메모리에서 페이징되므로 Batch Size 방식과 조합해야 함

### Q2. SP 사용 시 형상관리(버전 관리)는 어떻게 하는가?
- 원칙 : SP 소스를 DB에 두지 말고 `.sql` 파일로 Git 저장소에 둔다 (코드와 동일하게 관리)
- 마이그레이션 도구 : Flyway / Liquibase로 버전이 매겨진 스크립트를 앱 배포 시 자동 적용
- 배포 방식 : `CREATE OR REPLACE`로 멱등하게 작성해 반복 실행 가능하게 함
- 검증 : 배포 후 DB의 SP 정의와 Git의 파일을 비교(diff)하는 스크립트로 드리프트 감지
- 운영 규칙 : 운영 DB에서 직접 수정 금지, 반드시 PR -> 리뷰 -> 파이프라인 배포
- 그래도 남는 어려움 : 롤백이 코드처럼 간단하지 않고, 단위 테스트 도구가 빈약함

### Q3. 비즈니스 로직이 DB에 있으면 안 좋은 점은?
- 확장성 : 앱 서버는 Scale-out이 쉽지만 DB는 Scale-up이 한계 -> 가장 비싼 자원에 부하 집중
- 테스트 : 단위 테스트, Mock, 디버거 사용이 어렵고 IDE 지원도 약함
- 로직 분산 : 로직이 앱과 DB 양쪽에 흩어져 전체 흐름을 파악하기 어려움
- 종속성 : 벤더별 문법(PL/SQL, T-SQL)에 묶여 DB 교체가 사실상 불가능
- 인력 : SP 전문 개발자가 적어 유지보수 병목이 생김
- 예외 : 대량 배치, 집계처럼 "데이터 옆에서" 처리해야 이득인 로직은 SP가 합리적
