# ACID

> "은행 시스템을 설계 한다면 트랜잭션의 ACID를 어떻게 보장할 것인가? 각 항목이 실무에서 어떤 의미인지 하나씩 설명해 보시오"

## 트랜잭션(Transaction) 이란?
하나의 논리적 단위
> 여러 세부 작업을 '하나의 꾸러미'로 묶어서 처리하는 것.
> 
> [송금 시나리오]
> 
> 1. 내 계좌에서 1만원 차감 -> 2. 상대 계좌에 1만원 입금
> 
> 이 과정에서 서버가 꺼진다면? 그래서 ACID라는 안정장치가 필요함.

## Atomicity (원자성)
### "All or Nothing" 
트랜잭션 내의 모든 작업은 완벽히 수행되거나, 아예 수행되지 않아야 한다.
- Commit : 모두 성공 반영 
- Rollback : 장애 시 초기화

> 실우 원리 : DB 엔진은 작업을 수행하기 전의 데이터를 'Undo 로그'에 기록해둔다. 문제가 생기면 이 로그를 이용해 순식간에 이전 상태로 돌린다.

## Consistency (일관성)
### "데이터의 무결성 수호"
트랜잭션 전후로 데이터베이스는 미리 약속된 무결성 제약 조건을 항상 만족해야 한다.
- 도메인 제약 : 잔액 컬럼은 반드시 0 이상의 숫자여야 한다.
- 참조 무결성 : 존재하지 않는 회원 ID로는 주문을 생성할 수 없다.
- 유일성 제약 : 동일한 이메일 주소로 중복 가입할 수 없다.

> 엔진의 기능 : Primary Key / Foreign Key 제약, Not Null 설정, Check 제약 조건, Trigger 등을 통해 이 일관성을 강제로 유지한다.

## Isolation (고립성)
### "독립적인 병렬 처리'
동시에 실행되는 여러 트랜잭션이 서로의 작업에 간섭하지 못하도록 격리해야 한다.
"동시에 송금이 일어나도, DB 입장에서는 마치 하나씩 순서대로 처리되는 것처럼 보여야 함."
```
고립 수준(Isolation Level)
Read Uncommited < Read Commited < repeatable Read < Serializable
```

> 구현 기술 : DB는 Lock(잠금)이나 MVCC(다중 버전 동시 제어)를 사용하여 데이터 정합성을 유지한다.

## Durability (지속성)
### "영원한 기록"
성공적으로 완료 (Commit)된 트랜잭션 결과는 시스템 장애가 발생하더라도 사라지지 않고 영구적으로 보존되어야 한다.

- 비휘발성 저장소(SSD/HDD)에 기록 확정.
- 정전이나 운영체제 크래시 후 재부팅해도 복구 가능

> 핵심 기술: Write-Ahead Logging(WAL). 실제 데이터 페이지를 수정하기 전, 변경 로그를 먼저 디스크에 안전하게 기록하는 기술
