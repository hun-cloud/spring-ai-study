## 데이터베이스의 딜레마

> 한명씩 처리하면?
> 
> 정합성 : 완벽함 (데이터 꼬임 없음)
> 
> 성능 : 서비스 마비 (응답 속도 폭망)

> 마음대로 접근하면?
> 
> 성능 : 매우 빠름 (병렬 처리 극대화)
> 
> 정합성 : 데이터 엉망 (부정확한 결과)

### 격리 수준(Isolation Level)의 정의
"여러 트린잭션이 동시에 실행될 때, 다른 트랜잭션의 변경 데이터를 어느 정도까지 가시적으로 허용할 것인가를 결정하는 설정"

## 낮은 격리 수준의 3대 괴담 (ANSI 기준)
- Dirty Read : 남이 커밋도 안한(실패할 수도 있는) 데이터를 미리 읽어버리는 현상
- Non-repeatable Read : 같은 조회를 두 번 했는데 그 사이 남이 수정해서 결과가 달라지는 현상
- Phantom Read : 범위 조회를 했는데, 그 사이 남이 데이터를 삽입해서 없던게 귀신처럼 나타남

## Lv 0. READ UNCOMMITTED
### 개념 : '격리성 무시'

- 트랜잭션 변경 내역이 commit이나 Rollback에 상관없이 다른 트랜잭션에게 보인다. 
- 치명적 결함 : Dirty Read (존재하지도 않는 유령 데이터를 읽음)

```
Tx1 : Update 계좌 set 잔액 = 50 (진행중)
Tx2 : select 잔액 -> 50만원 읽음 (Dirty Read)
Tx1 : 서버 오류 발생 -> Rollback (실제 잔액은 0원)
```

## Lv 1. READ COMMITTED
### 개념 : '확정된 것만 읽는다.'
- 어떤 트랜잭션의 변경 내용이 Commit 되어야만 다른 트랜잭션이 조회할 수 있다.
- 해결 : Dirty Read 방지 성공
- 문제 : Non-repeatable Read 발생 가능 (조회할 때마다 값이 변함)
-> 현대 DBMS 상황 : Oracle, PostgreSQL의 기본 설정값이다.

 ```
Dirty Read 해결 & Non-repeatable Read 발생
Tx1 : Update 잔액 = 5- (Commit 전)
Tx2 : SELECT 잔액 -> 100만원 조회 (Dirty Read 방지)
Tx1 : COMMIT (수정 확정)
TX2 : 다시 SELECT 잔액 : 50만원 조회 (Non-repeatable Read)
 ```
"Commit 전 데이터는 숨겨주지만, 한 트랜잭션 내 조회가 달라지는 건 막지 못함."

## Lv 2. REPEATABLE READ
### 개념 : "처음 본 스냅샷 유지"
- 트랜잭션 내내 처음 읽은 데이터를 끝까지 유지해야 함
- 해결 : Non-repeatable Read 방지 성공
- 한계 : Phantom Read 발생 가능 (새로운 행 삽입 시 결과 행 개수 변화)
-> 현대 DBMS 상황 : MySQL InnoDB, PostgreSQL은 각자의 기술(Next-Key Lock, Snapshot Isolation) 으로 이 레벨에서 팬텀 리드까지 대부분 방어함.

```
TX1 : SELECT 잔액 -> 100만원 (Snapshot Read)
Tx2 : Update 잔액=50; Commit;
Tx1 : 다시 조회 -> 100만원 조회(반복 읽기 보장)
Tx2 : Insert ID=11 신규행; commit;
Tx2 : 범위 select -> 행 개수가 늘어남 (ANSI Phantom Read 현상)
```

## Lv3. SERIALIZABLE
### 개념 : "완벽한 격리"
- 트랜잭션들이 순차적으로 실행되는 것과 같은 결과를 보장
- 기술(ANSI) : 읽기 작업조차 공유 잠금(S-Lock)을 획득해야 함
- 해결 : Phantom Read 포함 모든 이상 현상 방지
-> 현대 DBMS 상황 : MySQL InnoDB는 모든 SELECT에 Shard Next-key Lock을 강제하여 인접 범위까지 모두 잠근다. 동시성이 최악으로 만들어지는 원인  

```
Tx1 : SELECT * WHERE 가격 > 100 (Shared Next-key Lock)
Tx2 : INSERT 상품 (가격=150) 시도 -> 무한 대기 (Wait... 범위 잠금 때문)
Tx1 : 다시 같은 SELECT -> 정합성 완벽 보장
Tx1 : COMMIT (락 해제)
Tx2 : 그제서야 삽입 수행
```
"현대 DB의 SERIALIZABLE은 단순 읽기에도 범위 락을 걸어 처리량이 수직 하강한다."

## 구현 원리 : MVCC & Undo Log
- 데이터를 수정할 떄 변경 전에 Undo Log 영역에 저장
- 즉 하나의 데이터에 대해서 여러 버전이 생길 수 있음.
- Snapshot Read : 데이터를 읽을 때 현재 값이 내 트랜잭션보다 최신이면, Undo 영역의 과거 데이터를 찾아가 읽는다. (락 없이 고립성 보장)

> MySQL InnoDB는 Next-Key Lock + Gap Lock 덕분에 Repeatable Read에서도 Phantom Read를 방지함.


## Next-Key Lock ? 
### 개념 : "레코드 락 + 그 앞의 갭 락" (InnoDB의 기본 락 방식)
- Record Lock : 인덱스 레코드 한 건 자체를 잠금 (그 행을 UPDATE/DELETE 못함)
- Gap Lock : 인덱스 레코드 "사이의 빈 공간"을 잠금 (그 사이에 INSERT 못함)
- Next-Key Lock = Record Lock + 바로 앞 Gap Lock -> 구간으로 표현하면 `(이전 레코드, 현재 레코드]`
- InnoDB는 REPEATABLE READ에서 **잠금 읽기(SELECT FOR UPDATE, UPDATE, DELETE)** 로 인덱스 범위를 스캔할 때 지나간 모든 레코드에 Next-Key Lock을 건다.
- 마지막 레코드 뒤의 무한 구간은 supremum(가상의 최댓값 레코드)에 락을 걸어서 막는다.

```
id 인덱스에 10, 20, 30 이 있을 때
Tx1 : SELECT * FROM t WHERE id BETWEEN 15 AND 25 FOR UPDATE;
      -> 잠기는 구간 : (10, 20], (20, 30]   (레코드 20 + 그 앞뒤 갭)
Tx2 : INSERT id=17  -> 대기 (갭 (10,20) 잠김)
Tx2 : INSERT id=27  -> 대기 (갭 (20,30) 잠김)
Tx2 : INSERT id=35  -> 성공 (범위 밖)
Tx2 : UPDATE id=20  -> 대기 (레코드 락)
Tx2 : UPDATE id=10  -> 성공 (10은 갭의 경계일 뿐, 레코드 자체는 안 잠김)
```

- 예외 : **유니크 인덱스로 = 조건 검색해서 행이 존재**하면 갭이 필요 없으므로 Record Lock 만 건다. (`WHERE pk = 20 FOR UPDATE` 는 20 한 건만 잠금)
- 주의 : WHERE 절에 인덱스가 없으면 풀스캔이 되고, 테이블의 **모든 레코드와 모든 갭**이 잠긴다. (사실상 테이블 락)

"Next-Key Lock은 '내가 본 행'뿐 아니라 '내가 본 범위' 자체를 잠가서, 그 사이에 유령 행이 끼어들지 못하게 한다."

## Gap Lock ?
### 개념 : "존재하지 않는 행을 잠근다"
- 잠그는 대상이 레코드가 아니라 **레코드 사이의 간격(열린 구간)** 이다. 목적은 오직 하나, 그 구간에 대한 **INSERT 차단**.
- 갭 락끼리는 서로 충돌하지 않는다. Tx1과 Tx2가 같은 갭에 동시에 갭 락을 잡을 수 있다. (둘 다 "여기 INSERT 막아줘" 라는 뜻이라 목적이 같음)
- 그래서 갭 락은 "내가 뭘 하겠다"는 락이 아니라 "남이 INSERT 못하게 하는" **순수 억제용(purely inhibitive)** 락이다.
- READ COMMITTED 에서는 갭 락을 **사용하지 않는다.** (외래키 검사, 중복 키 검사 등 예외 제외) -> 그래서 RC에서는 Phantom Read가 허용된다.
- 잠금 읽기가 **존재하지 않는 값**을 찾을 때도 갭 락이 걸린다. (`WHERE id = 25 FOR UPDATE` 인데 25가 없으면 (20, 30) 갭이 잠김)

```
갭 락 데드락의 전형적인 패턴 (RR, id=25 없음)
Tx1 : SELECT * FROM t WHERE id = 25 FOR UPDATE;  -> 갭 (20,30) 락
Tx2 : SELECT * FROM t WHERE id = 25 FOR UPDATE;  -> 갭 (20,30) 락 (갭 락끼리는 호환되니 성공)
Tx1 : INSERT id = 25  -> 대기 (Tx2의 갭 락에 막힘)
Tx2 : INSERT id = 25  -> 대기 (Tx1의 갭 락에 막힘) => Deadlock! InnoDB가 한쪽을 롤백
```
-> "없으면 INSERT, 있으면 UPDATE" 를 SELECT FOR UPDATE + INSERT 로 구현하면 이 패턴을 만난다. `INSERT ... ON DUPLICATE KEY UPDATE` 나 유니크 제약 + 예외 처리로 푸는 게 안전하다.

"Gap Lock은 Phantom을 막아주는 대가로, RR에서 데드락과 대기 시간을 늘리는 주범이다. RC로 내리면 갭 락이 사라져 처리량이 오르는 이유가 여기 있다."

## 꼬리질문 

### 왜 Oracle은 READ COMMITED를, MySQL은 REPEATABLE READ를 기본으로 쓰나요? PostgreSQL은?

**Oracle : READ COMMITTED**
- Oracle은 애초에 REPEATABLE READ 레벨이 **없다.** READ COMMITTED, SERIALIZABLE, READ ONLY 세 가지뿐.
- Oracle의 철학은 "읽기는 절대 쓰기를 막지 않고, 쓰기도 읽기를 막지 않는다." Undo 세그먼트 기반 MVCC로 **문장(statement) 단위 일관성**을 보장하면 대부분의 OLTP에 충분하다고 본다.
- 트랜잭션 단위 스냅샷을 오래 유지하면 Undo가 재사용되어 `ORA-01555 snapshot too old` 가 터질 위험이 커진다. 짧은 문장 단위 스냅샷이 처리량과 안정성 모두에 유리하다.

**MySQL InnoDB : REPEATABLE READ**
- 역사적인 이유가 크다. MySQL 복제(Replication)는 오랫동안 **Statement 기반 바이너리 로그**(실행한 SQL 문장 자체를 복제)를 썼다.
- 문장을 그대로 다시 실행해서 Master와 Slave가 같은 결과가 나오려면, 문장이 실행되는 동안 다른 트랜잭션이 그 범위에 끼어들지 못해야 한다. -> 갭 락이 있는 RR이 필요했다.
- 실제로 MySQL은 지금도 RC + STATEMENT 바이너리 로그 조합이면 에러를 낸다. RC를 쓰려면 `binlog_format=ROW`가 강제된다.
- 즉 "정합성을 더 사랑해서"가 아니라 **복제 일관성 때문에 선택된 기본값**이고, 지금은 ROW 로그가 기본이라 실무에서는 RC로 내려 쓰는 경우가 많다.

**PostgreSQL : READ COMMITTED**
- SQL 표준의 기본값은 SERIALIZABLE 이지만 성능 때문에 대부분 DB가 RC를 택했고 PostgreSQL도 Oracle과 같은 이유로 RC.
- 특징 1 : READ UNCOMMITTED를 설정해도 **RC로 동작**한다. (MVCC 구조상 Dirty Read를 만들 수가 없음)
- 특징 2 : PostgreSQL의 REPEATABLE READ는 사실상 **Snapshot Isolation** 이라 락 없이 Phantom Read까지 막는다. 대신 갱신 충돌 시 대기 후 에러(`could not serialize access`)를 내고, 애플리케이션이 재시도해야 한다.
- 특징 3 : SERIALIZABLE은 락이 아니라 **SSI(Serializable Snapshot Isolation)** 로 구현. 읽기/쓰기 의존성을 추적해 직렬화 불가능한 조합만 골라 롤백시킨다. MySQL처럼 읽기에 범위 락을 걸지 않아 동시성이 훨씬 좋지만, **재시도 로직이 필수**다.

"세 DB 모두 MVCC지만, 기본값을 정한 이유는 다르다. Oracle/PostgreSQL은 처리량, MySQL은 Statement 복제 호환성."

### REPEATABLE READ에서 Phantom READ가 발생하는 결정적인 이유는?
- 락 기반(ANSI) RR은 **"읽은 행"에만 락을 건다.** 행 락은 이미 존재하는 행에만 걸 수 있다.
- INSERT되는 행은 아직 존재하지 않으므로 **잠글 대상 자체가 없다.** 그래서 `WHERE 가격 > 100` 같은 **조건(범위)** 을 보호하려면 행 락이 아니라 범위 락(Gap/Predicate Lock)이나 스냅샷이 필요하다.
- 한 줄로 : Non-repeatable Read는 "행의 값"이 바뀌는 문제라 행 락으로 막히지만, Phantom Read는 "조건에 맞는 행의 집합"이 바뀌는 문제라 행 락으로는 막을 수 없다.

**MySQL InnoDB RR 에서도 Phantom을 볼 수 있는 경우 (Snapshot Read와 Current Read의 혼용)**
- 일반 SELECT = Snapshot Read (트랜잭션 시작 시점 스냅샷)
- UPDATE / DELETE / SELECT FOR UPDATE = **Current Read** (최신 커밋 데이터를 읽고 락)
- 두 종류를 한 트랜잭션에서 섞으면 스냅샷이 깨진다.

```
Tx1 : SELECT * FROM t WHERE age > 20;         -> 5건 (스냅샷)
Tx2 : INSERT INTO t (age) VALUES (25); COMMIT;
Tx1 : UPDATE t SET flag = 1 WHERE age > 20;   -> 6건 갱신 (Current Read, 새 행도 보임)
Tx1 : SELECT * FROM t WHERE age > 20;         -> 6건!  (내가 갱신한 행은 내 스냅샷에 보임)
```
-> Tx1은 처음에 5건을 봤는데, 남이 커밋한 행이 어느새 내 결과에 끼어들어 6건이 된다. InnoDB RR이 "Phantom을 완벽히 막는다"고 말할 수 없는 이유.

"결정적인 이유는 '없는 행은 잠글 수 없다'. 그리고 MVCC DB에서는 '스냅샷 읽기와 현재 읽기가 다른 세계를 본다'."

## SELECT FOR UPDATE는 언제 사용해야 합니까?
### 개념 : "읽은 값을 근거로 쓸 거면, 읽을 때부터 잠가라" (비관적 락, Pessimistic Lock)
- 조회한 행에 배타적 락(X-Lock)을 걸어 트랜잭션이 끝날 때까지 다른 트랜잭션의 UPDATE/DELETE/FOR UPDATE를 막는다.
- 일반 SELECT(스냅샷 읽기)는 락을 안 걸기 때문에, **"읽고 -> 판단하고 -> 쓰는"** 패턴에서 그 사이에 남이 값을 바꾸는 것을 막지 못한다. (Lost Update)

```
Lost Update : 잔액 100원, 두 요청이 동시에 70원 출금
Tx1 : SELECT 잔액 -> 100  (충분하다고 판단)
Tx2 : SELECT 잔액 -> 100  (충분하다고 판단)
Tx1 : UPDATE 잔액 = 30; COMMIT;
Tx2 : UPDATE 잔액 = 30; COMMIT;   -> 140원 출금됐는데 잔액 30원

SELECT FOR UPDATE 적용
Tx1 : SELECT 잔액 FOR UPDATE -> 100 (락 획득)
Tx2 : SELECT 잔액 FOR UPDATE -> 대기...
Tx1 : UPDATE 잔액 = 30; COMMIT; (락 해제)
Tx2 : -> 30 조회 -> 잔액 부족 -> 거절
```

### 써야 하는 경우
1. **읽은 값에 따라 쓰기 결과가 달라질 때** : 잔액 확인 후 출금, 재고 확인 후 차감, 좌석 확인 후 예약, 쿠폰 잔여 수량 확인 후 발급
2. **하나의 행을 여러 요청이 동시에 갱신하는데, 실패보다 대기가 나을 때** : 충돌이 잦아서 낙관적 락으로 하면 재시도가 너무 많이 발생하는 경우
3. **여러 테이블/행을 한 세트로 일관되게 바꿔야 할 때** : 부모 행을 먼저 잠가서 자식 행 동시 수정을 직렬화 (주문 헤더 잠그고 주문 상세 수정)
4. **작업 큐 / 배치에서 한 건씩 선점할 때** : `FOR UPDATE SKIP LOCKED` (MySQL 8.0+, PostgreSQL) 로 이미 잠긴 건은 건너뛰며 여러 워커가 서로 다른 행을 가져간다.

### 쓰지 말아야 하는 경우 / 대안
- **단순 증감** 이라면 락 없이 원자적 UPDATE 한 줄로 끝낸다. UPDATE는 Current Read라서 그 자체가 안전하다.
  `UPDATE stock SET qty = qty - 1 WHERE id = ? AND qty > 0` -> 영향받은 행이 0이면 재고 부족
- **충돌이 드문 경우** 낙관적 락(version 컬럼, JPA `@Version`)이 락 대기 없이 처리량이 더 좋다. 충돌 시 예외 -> 재시도.
- **트래픽이 매우 몰리는 핫 로우**(인기 상품 1개 재고, 전역 카운터)는 DB 락으로 직렬화하면 DB 커넥션이 전부 대기 상태로 묶인다. Redis 분산 락/원자 연산, 메시지 큐로 직렬화하는 것을 고려.
- **읽기만 하고 안 쓸 거면** 절대 쓰지 않는다. 남의 갱신만 막는다. 값이 바뀌지 않는 걸 보장하고 싶을 뿐이면 `FOR SHARE`(S-Lock)가 맞다.

### 사용 시 주의사항
- **반드시 트랜잭션 안에서** 사용. 락은 COMMIT/ROLLBACK 시점에 풀리므로, autocommit 상태에서는 문장이 끝나는 순간 풀려서 의미가 없다. (Spring `@Transactional` 필수)
- **WHERE 절 컬럼에 인덱스가 있어야 한다.** 없으면 스캔한 모든 행(+RR이면 모든 갭)이 잠긴다.
- **RR에서는 갭 락도 함께 걸린다.** 범위 조건이나 존재하지 않는 값 조회 시 INSERT가 막히고 데드락 위험이 커진다. 정확히 그 행만 잠그고 싶으면 PK/유니크 = 조건으로 조회하거나, RC로 낮춘다.
- **락 획득 순서를 통일** 한다. Tx1은 A->B, Tx2는 B->A 순으로 잠그면 데드락. 항상 PK 오름차순 등 한 방향으로.
- **트랜잭션을 짧게.** 락을 잡은 채로 외부 API 호출, 파일 IO 등을 하면 그동안 다른 요청이 전부 대기한다.
- 대기 정책 : `NOWAIT` (잠겨 있으면 즉시 에러), `SKIP LOCKED` (잠긴 행 건너뜀), 기본은 `innodb_lock_wait_timeout`(기본 50초)까지 대기.
- JPA : `@Lock(LockModeType.PESSIMISTIC_WRITE)` -> `SELECT ... FOR UPDATE` 로 변환됨. 타임아웃은 `@QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000"))`.

"SELECT FOR UPDATE는 '읽은 값을 믿고 쓸 때' 쓰는 도구다. 단순 증감은 원자적 UPDATE로, 충돌이 드물면 낙관적 락으로, 트래픽이 극단적이면 DB 밖에서 직렬화하는 것이 먼저다."

## 정리
1. 격리 수준은 동시에 실행되는 트랜잭션들이 서로 어느 정도까지 데이터를 볼 수 있는지를 결정하는 정책
2. 낮은 수준은 동시 처리량이 높지만 Dirty Read 같은 정합성 오류가 발생하며, 높은 수준은 Lock으로 인한 성능 병목 발생
3. 실무에서는 성능을 위해 READ COMMITTED를 주로 사용하며, 정산처럼 높은 일관성이 중요한 경우 REPEATABLE 기반에 비관적 락(SELECT FOR UPDATE)를 조합하여 필요한 행만 명시적으로 잠그는 전략을 선택한다.
