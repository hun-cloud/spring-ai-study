# @Transactional 동작 원리와 트랜잭션 전파 옵션

> "@Transactional 붙이면 알아서 되는 거 아닌가요?" -> 프록시가 대신 해주는 것이다.
> 그래서 프록시를 거치지 않는 호출(자기 자신 호출, private 메서드)에서는 아무 일도 일어나지 않는다.

---

## 1. @Transactional은 어떻게 동작하나요?

### 핵심 한 줄
**Spring AOP 프록시**가 진짜 객체를 감싸고, 메서드 호출 앞뒤에서 `begin / commit / rollback`을 대신 수행한다.

### 쉬운 비유
- 진짜 서비스 객체 = 요리사
- 프록시 = 홀 매니저
- 손님(호출자)은 항상 매니저를 통해 주문한다. 매니저가 "주문 시작(begin)"을 기록하고, 요리가 끝나면 "정상 완료(commit)" 또는 "취소(rollback)"를 처리한다.
- 요리사가 주방 안에서 스스로 다른 요리를 만드는 것(내부 호출)은 매니저가 볼 수 없다.

### 동작 흐름
```
Controller
   │
   ▼
[ Proxy(서비스를 상속한 CGLIB 클래스) ]
   │  1. TransactionInterceptor.invoke()
   │  2. PlatformTransactionManager.getTransaction()  -> 커넥션 획득, setAutoCommit(false)
   │  3. 커넥션을 TransactionSynchronizationManager(ThreadLocal)에 바인딩
   ▼
[ 실제 Service.method() ]
   │  Repository는 같은 ThreadLocal에서 커넥션을 꺼내 쓴다 -> 같은 트랜잭션
   ▼
   4. 정상 종료 -> commit
      RuntimeException / Error -> rollback
   5. 커넥션 반납, ThreadLocal 정리
```

### 프록시가 만들어지는 과정
1. 컨테이너가 빈을 생성할 때 `@Transactional`이 붙은 클래스/메서드가 있는지 확인 (`BeanPostProcessor`)
2. 있으면 진짜 객체 대신 **프록시 객체**를 빈으로 등록
3. Spring Boot 기본값은 **CGLIB 프록시** (클래스를 상속해서 서브클래스 생성). 인터페이스 기반 JDK 동적 프록시는 `proxyTargetClass=false`로 설정했을 때만 사용
4. 다른 빈에 주입되는 것은 항상 이 프록시다 -> 그래서 `@Autowired` 받은 객체 클래스명을 찍어보면 `OrderService$$SpringCGLIB$$0` 처럼 나온다

### 롤백 규칙 (자주 나오는 함정)
- 기본값 : **RuntimeException, Error 만 롤백**. Checked Exception(`IOException`, `SQLException` 등)은 **커밋**된다.
- Checked 예외도 롤백하려면 `@Transactional(rollbackFor = Exception.class)`
- 예외를 메서드 안에서 `try-catch`로 잡아버리면 프록시는 예외를 보지 못하므로 커밋된다.

```java
@Transactional
public void order() {
    try {
        payment.pay();      // 여기서 RuntimeException
    } catch (Exception e) {
        log.error("결제 실패", e);   // 삼켜버림 -> 프록시는 정상 종료로 인식 -> commit
    }
}
```

## 2. 같은 클래스 내부 메서드 호출 시 트랜잭션이 적용 안 되는 이유는? (Self-Invocation)

### 문제 코드
```java
@Service
public class MemberService {

    public void register(Member m) {   // @Transactional 없음
        saveMember(m);                 // this.saveMember(m) -> 프록시를 거치지 않음
    }

    @Transactional
    public void saveMember(Member m) { // 트랜잭션이 걸릴 것 같지만 안 걸림
        memberRepository.save(m);
    }
}
```

### 왜 안 되는가
- 외부에서 `memberService.register()`를 호출하면 프록시를 통해 들어온다. 하지만 `register()`에는 `@Transactional`이 없으니 프록시는 그냥 통과시킨다.
- `register()` 안에서 `saveMember()`를 호출할 때의 `this`는 **프록시가 아니라 진짜 객체**다.
- 진짜 객체의 메서드를 직접 부르니 `TransactionInterceptor`가 끼어들 틈이 없다.

```
외부 호출:  caller -> [Proxy] -> target.register()
내부 호출:                        target.register() -> this.saveMember()   (Proxy 없음!)
```

### 반대 케이스도 동일하게 무시된다
```java
@Transactional                 // 외부 REQUIRED
public void outer() {
    inner();                   // 아래 REQUIRES_NEW는 무시되고 outer 트랜잭션에 그대로 참여
}

@Transactional(propagation = Propagation.REQUIRES_NEW)
public void inner() { ... }
```
-> 전파 옵션을 바꿔도 내부 호출이면 **적용되지 않는다.** 실무에서 "REQUIRES_NEW 붙였는데 왜 같이 롤백되죠?"의 원인 1순위.

### 해결 방법
| 방법 | 설명 | 비고 |
|---|---|---|
| **클래스 분리 (권장)** | 트랜잭션이 필요한 메서드를 별도 빈으로 뽑아서 주입받아 호출 | 가장 깔끔, 책임 분리도 됨 |
| 자기 자신 주입 | `@Autowired private MemberService self;` 후 `self.saveMember()` | 순환 참조 경고, `@Lazy` 필요할 수 있음 |
| `TransactionTemplate` | 프로그래밍 방식으로 트랜잭션 범위를 직접 지정 | 선언적 방식 포기 |
| `AopContext.currentProxy()` | `@EnableAspectJAutoProxy(exposeProxy = true)` 후 프록시를 꺼내 호출 | 코드가 AOP에 의존, 비권장 |
| AspectJ 위빙 | 프록시가 아니라 바이트코드에 직접 삽입 | 설정 복잡, 실무에서 드묾 |

```java
// 권장: 클래스 분리
@Service
@RequiredArgsConstructor
public class MemberService {
    private final MemberWriter memberWriter;   // 별도 빈 (프록시)

    public void register(Member m) {
        memberWriter.save(m);                  // 프록시를 거침 -> 트랜잭션 적용
    }
}
```

## 3. private 메서드에 붙이면 어떻게 되나요?

### 결론
**아무 일도 일어나지 않는다.** 예외도 없고 경고도 없이 조용히 무시된다. (IDE는 경고를 보여준다)

### 이유
- CGLIB 프록시는 **원본 클래스를 상속한 서브클래스**다. 서브클래스는 부모의 `private` 메서드를 **오버라이드할 수 없다.**
- 오버라이드가 안 되니 프록시가 가로챌 방법이 없다.
- 같은 이유로 **`final` 메서드, `final` 클래스**에도 적용되지 않는다.
- `static` 메서드도 인스턴스 프록시 대상이 아니므로 불가.

### 접근 제어자별 정리
| 접근 제어자 | CGLIB 프록시 (Boot 기본) | JDK 동적 프록시 (인터페이스) |
|---|---|---|
| public | O | O |
| protected | Spring 6.0+ O (5.x 이하 X) | X |
| package-private | Spring 6.0+ O (5.x 이하 X) | X |
| private | **X** | **X** |
| final | **X** | 해당 없음 |

> 실무 원칙 : `@Transactional`은 **public 메서드**에만 붙인다. private 메서드에서 트랜잭션이 필요하면 그 메서드를 호출하는 public 메서드에 붙이거나(같은 트랜잭션에 포함), 별도 빈으로 분리한다.

## 4. 전파 옵션 (Propagation)

### 전파(Propagation)란?
> "이미 진행 중인 트랜잭션이 있을 때, 새로 호출된 `@Transactional` 메서드가 **기존 트랜잭션에 참여할지, 새로 만들지, 거부할지**"를 정하는 규칙

### 용어 먼저
- **물리 트랜잭션** : 실제 DB 커넥션 한 개에서 `begin ~ commit/rollback`까지. 커넥션 단위.
- **논리 트랜잭션** : `@Transactional` 메서드 하나하나의 범위. 여러 논리 트랜잭션이 하나의 물리 트랜잭션을 공유할 수 있다.
- 원칙 : **논리 트랜잭션 중 하나라도 롤백되면 물리 트랜잭션은 롤백된다.** (아래 `UnexpectedRollbackException`에서 다시 나옴)

### 7가지 옵션 한눈에
| 옵션 | 기존 트랜잭션 있을 때 | 기존 트랜잭션 없을 때 | 사용 시나리오 |
|---|---|---|---|
| **REQUIRED** (기본값) | 참여 | 새로 생성 | 대부분의 비즈니스 로직 |
| **REQUIRES_NEW** | 기존 것을 **일시 중단**하고 **새 물리 트랜잭션** 생성 | 새로 생성 | 로그/이력/알림 등 본 로직과 독립적으로 커밋해야 하는 작업 |
| **NESTED** | 기존 트랜잭션 안에 **Savepoint** 생성 | 새로 생성 (REQUIRED와 동일) | 일부만 롤백하고 나머지는 계속 진행 (배치 일부 실패 허용) |
| SUPPORTS | 참여 | 트랜잭션 없이 실행 | 조회 메서드. 있으면 타고 없으면 말고 |
| NOT_SUPPORTED | 기존 것을 일시 중단하고 **트랜잭션 없이** 실행 | 트랜잭션 없이 실행 | 트랜잭션 안에서 오래 걸리는 외부 API 호출을 분리할 때 |
| MANDATORY | 참여 | **예외** (`IllegalTransactionStateException`) | "반드시 트랜잭션 안에서만 호출돼야 한다"를 강제 |
| NEVER | **예외** | 트랜잭션 없이 실행 | "트랜잭션 안에서 절대 호출되면 안 된다"를 강제 |

### REQUIRED 동작 (기본값)
```
outer (REQUIRED) ──┐
                   ├── 물리 트랜잭션 1개 (커넥션 1개)
inner (REQUIRED) ──┘   inner는 outer에 참여. commit/rollback 결정권은 outer(최초 시작자)에게만 있음
```
- 내부 메서드가 정상 종료해도 커밋하지 않는다. 실제 커밋은 **가장 바깥 트랜잭션**이 끝날 때 한 번.
- 내부 메서드에서 예외가 나면 내부 트랜잭션은 **rollback-only 마킹**만 한다.

#### 함정 : UnexpectedRollbackException
```java
@Transactional
public void outer() {
    try {
        inner();                // REQUIRED, 여기서 RuntimeException -> rollback-only 마킹
    } catch (Exception e) {
        // 예외를 잡았으니 계속 진행할 수 있을 것 같지만...
    }
    // outer 정상 종료 -> commit 시도
    // -> 이미 rollback-only 마킹됨 -> UnexpectedRollbackException 발생, 전체 롤백
}
```
- "예외 잡았는데 왜 롤백돼요?"의 정체. 내부 트랜잭션이 물리 트랜잭션에 이미 **롤백 도장**을 찍어놔서 outer가 커밋을 못 한다.
- 이 상황이 바로 **REQUIRES_NEW 또는 NESTED가 필요한 순간**이다.

## 5. REQUIRES_NEW vs NESTED (핵심 : 외부 롤백의 영향을 받는가)

### 구조 비교
```
[REQUIRES_NEW]                          [NESTED]
outer ── 물리 Tx A (커넥션 1)            outer ── 물리 Tx A (커넥션 1)
  │  (A 일시 중단)                         │
  └─ inner ── 물리 Tx B (커넥션 2)         └─ inner ── Tx A 안의 Savepoint
       B commit -> 즉시 DB 반영                  inner 성공 -> savepoint 해제(커밋 아님)
  (A 재개)                                       inner 실패 -> savepoint까지만 롤백
  A commit / rollback                            A commit 시 inner 내용도 함께 커밋
```

### 차이 정리
| 비교 항목 | REQUIRES_NEW | NESTED |
|---|---|---|
| 물리 트랜잭션 | **별도** (새 커넥션) | 외부와 **동일** (Savepoint) |
| 커넥션 개수 | **2개** (외부 커넥션은 반납 안 하고 대기) | 1개 |
| 내부 실패 -> 외부 영향 | 없음 (예외를 catch만 하면) | 없음 (savepoint까지만 롤백) |
| **외부 실패 -> 내부 영향** | **없음. 내부는 이미 커밋됨** | **함께 롤백됨** |
| 내부 커밋 시점 | 내부 메서드 종료 즉시 | 외부 트랜잭션 커밋 시 |
| 외부에서 내부 변경 내용을 볼 수 있나 | 격리 수준에 따라 (커밋됐으니 READ COMMITTED 이상이면 보임) | 같은 트랜잭션이므로 당연히 보임 |
| JPA/Hibernate 지원 | O | **X** (`NestedTransactionNotSupportedException`) |
| JDBC(JdbcTemplate, MyBatis) 지원 | O | O (드라이버 Savepoint 지원 필요) |

### 한 줄 요약
- **REQUIRES_NEW** : "본 로직이 실패하더라도 **이건 반드시 남겨야 한다**" -> 완전 독립
- **NESTED** : "이 부분만 실패하면 **이 부분만 되돌리고** 나머지는 계속 가자. 단, 전체가 실패하면 **같이 사라져도 된다**" -> 부분 롤백

### NESTED 사용 예 (부분 실패 허용 배치)
```java
@Transactional
public void importAll(List<Row> rows) {
    for (Row row : rows) {
        try {
            rowImporter.importOne(row);   // NESTED. 한 건 실패 -> 그 건만 savepoint 롤백
        } catch (Exception e) {
            failed.add(row);
        }
    }
    // 여기서 예외 나면 성공했던 건들도 전부 롤백 (같은 물리 Tx)
}
```
-> JPA 프로젝트에서는 못 쓴다. 그래서 실무에서 NESTED를 실제로 쓴 경험은 드물고, 대부분 REQUIRES_NEW로 해결한다.

## 6. 실무 : REQUIRED 외에 뭘 써봤는지 -> REQUIRES_NEW로 로그/이력 저장

### 상황
- 정책 적용 / 결제 / 배치 같은 **본 작업**을 수행하고, 성공이든 실패든 **이력 테이블에 결과를 남겨야** 한다.
- 특히 **실패 이력**이 중요하다. 운영자가 "왜 실패했는지"를 이력 화면에서 봐야 한다.

### 잘못된 구현 1 : 같은 트랜잭션에서 이력 저장
```java
@Transactional
public void applyPolicy(Policy p) {
    try {
        enforcer.apply(p);                         // 실패 -> RuntimeException
        historyRepository.save(History.success(p));
    } catch (Exception e) {
        historyRepository.save(History.fail(p, e)); // 저장은 했지만...
        throw e;                                   // 예외 전파 -> 전체 롤백 -> 실패 이력도 사라짐
    }
}
```
- 실패 이력을 저장했는데 **본 작업과 함께 롤백**되어 이력이 남지 않는다.
- 예외를 던지지 않으면 이력은 남지만, 본 작업의 부분 변경이 **커밋**되어 데이터가 꼬인다.

### 잘못된 구현 2 : 같은 클래스에 REQUIRES_NEW 붙이기
```java
@Transactional
public void applyPolicy(Policy p) {
    try { enforcer.apply(p); }
    catch (Exception e) { saveFailHistory(p, e); throw e; }
}

@Transactional(propagation = Propagation.REQUIRES_NEW)  // 무시됨! (self-invocation)
public void saveFailHistory(Policy p, Exception e) { ... }
```
-> 2번 항목의 자기 호출 문제. REQUIRES_NEW가 적용되지 않아 결과는 잘못된 구현 1과 같다.

### 올바른 구현 : 이력 저장을 별도 빈 + REQUIRES_NEW
```java
@Service
@RequiredArgsConstructor
public class PolicyHistoryService {

    private final PolicyHistoryRepository historyRepository;

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveFail(Policy p, Exception e) {
        historyRepository.save(History.fail(p, e.getMessage()));
        // 메서드 종료 시 즉시 커밋. 바깥이 롤백돼도 이 row는 남는다.
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveSuccess(Policy p) {
        historyRepository.save(History.success(p));
    }
}

@Service
@RequiredArgsConstructor
public class PolicyService {

    private final Enforcer enforcer;
    private final PolicyHistoryService historyService;   // 다른 빈 -> 프록시를 거침

    @Transactional
    public void applyPolicy(Policy p) {
        try {
            enforcer.apply(p);
            historyService.saveSuccess(p);
        } catch (Exception e) {
            historyService.saveFail(p, e);   // 새 커넥션에서 즉시 커밋
            throw e;                         // 본 작업은 롤백
        }
    }
}
```

### 실행 순서
```
1. applyPolicy 시작        -> 커넥션 #1 획득, Tx A begin
2. enforcer.apply 실패     -> RuntimeException
3. historyService.saveFail -> Tx A 일시 중단, 커넥션 #2 획득, Tx B begin
4. 이력 INSERT             -> Tx B commit, 커넥션 #2 반납   <- 이력 확정
5. Tx A 재개, 예외 재던짐   -> Tx A rollback, 커넥션 #1 반납 <- 본 작업 취소
```

### 이때 깊게 파고들었던 주의점들

#### (1) REQUIRES_NEW 메서드 안의 예외는 반드시 처리해야 한다
```java
try {
    historyService.saveFail(p, e);
} catch (Exception historyEx) {
    log.error("이력 저장 실패", historyEx);   // 이력 저장이 실패해도 본 로직의 예외 흐름을 덮어쓰지 않도록
}
throw e;
```
- 이력 저장에서 예외가 나면 그 예외가 바깥으로 올라가면서 **원래 실패 원인(e)이 가려진다.**
- 이력은 부수 작업이므로 실패해도 본 흐름을 망치지 않게 격리한다.

#### (2) 커넥션을 2개 잡는다 -> 커넥션 풀 데드락
- REQUIRES_NEW 중에는 바깥 트랜잭션의 커넥션 #1을 **반납하지 않고 들고 있다.**
- HikariCP `maximumPoolSize = 10`인데 동시 요청 10개가 모두 `applyPolicy`에 들어오면?
  - 10개 스레드가 커넥션 #1을 각각 하나씩 점유 -> 풀 고갈
  - 각자 커넥션 #2를 기다림 -> **아무도 못 얻음 -> 전부 `connectionTimeout`(기본 30초) 후 실패**
- 이건 DB 데드락이 아니라 **풀 레벨 데드락**이다. DB 쪽 로그에는 아무것도 안 남아서 원인 찾기 어렵다.
- 대응 : HikariCP 공식 문서 공식 `pool size = Tn x (Cm - 1) + 1` (Tn: 최대 스레드 수, Cm: 스레드당 동시 필요 커넥션 수). REQUIRES_NEW 한 번이면 Cm = 2.
- 관련 정리 : `01_DB Connection Pool 몇개로 설정해야 할까.md`

#### (3) "본 작업은 롤백됐는데 성공 이력이 남는" 역방향 문제
```java
@Transactional
public void applyPolicy(Policy p) {
    enforcer.apply(p);
    historyService.saveSuccess(p);   // REQUIRES_NEW -> 여기서 커밋됨
    auditService.record(p);          // 여기서 실패 -> 본 작업 롤백. 하지만 성공 이력은 이미 커밋됨
}
```
- REQUIRES_NEW는 **먼저 커밋**되기 때문에 뒤에서 바깥이 실패하면 "성공했다는 이력만 남고 실제 데이터는 없는" 불일치가 생긴다.
- 성공 이력은 REQUIRES_NEW로 저장하면 안 되고, **본 트랜잭션에 포함(REQUIRED)** 시키거나 **커밋 이후 시점**에 저장해야 한다.
- 즉, **실패 이력 = REQUIRES_NEW, 성공 이력 = REQUIRED 또는 AFTER_COMMIT** 으로 나눠서 생각해야 한다.

#### (4) 대안 : 트랜잭션 이벤트로 시점을 분리
```java
// 발행
@Transactional
public void applyPolicy(Policy p) {
    enforcer.apply(p);
    eventPublisher.publishEvent(new PolicyAppliedEvent(p));
}

// 구독: 커밋이 확정된 뒤에만 실행
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
@Transactional(propagation = Propagation.REQUIRES_NEW)   // AFTER_COMMIT 시점엔 원래 Tx가 끝났으므로 새 Tx 필요
public void onApplied(PolicyAppliedEvent e) {
    historyRepository.save(History.success(e.policy()));
}

// 롤백된 뒤에만 실행
@TransactionalEventListener(phase = TransactionPhase.AFTER_ROLLBACK)
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void onFailed(PolicyFailedEvent e) { ... }
```
- 이력 저장 시점을 "커밋 확정 후 / 롤백 확정 후"로 고정하므로 (3)의 불일치가 사라진다.
- 단점 : `AFTER_COMMIT` 리스너 안에서 기본 REQUIRED로는 DB 쓰기가 반영되지 않는다(이미 커밋된 Tx에 참여하는 형태). **REQUIRES_NEW를 꼭 붙여야 한다.** 이걸 몰라서 "리스너에서 저장했는데 왜 안 들어가요?"가 자주 나온다.

#### (5) 이력 저장이 많거나 느리면 -> 비동기/큐로 분리
- 이력이 대량이거나 외부 저장소(ES, Kafka)면 트랜잭션에서 완전히 떼어낸다. `@Async` + 이벤트, 또는 메시지 큐.
- 이때는 "이력이 유실될 수 있음"을 감수하는 설계. 감사(Audit) 목적으로 유실이 허용되지 않으면 Outbox 패턴을 고려.

### 실무 선택 기준 정리
| 요구사항 | 선택 |
|---|---|
| 본 작업 실패 시 실패 이력을 **반드시** 남긴다 | **REQUIRES_NEW** (별도 빈, 예외 catch 필수) |
| 본 작업 성공 시에만 성공 이력을 남긴다 | REQUIRED로 같은 Tx에 포함, 또는 `AFTER_COMMIT` 이벤트 + REQUIRES_NEW |
| 여러 건 중 일부 실패는 건너뛰고 나머지는 저장 | NESTED (JDBC만), JPA면 건별 REQUIRES_NEW 또는 애플리케이션 레벨 분리 |
| 트랜잭션 안에서 외부 API 호출을 해야 한다 | NOT_SUPPORTED로 분리, 또는 커밋 후 이벤트로 호출 |
| 이 메서드는 무조건 트랜잭션 안에서만 불려야 한다 | MANDATORY로 강제 (Repository 계층 방어) |

## 7. 면접 답변용 요약

**Q. @Transactional은 어떻게 동작하나요?**
> Spring AOP 프록시 기반입니다. 빈 생성 시 CGLIB 프록시가 원본을 감싸고, 호출이 들어오면 `TransactionInterceptor`가 `TransactionManager`를 통해 커넥션을 얻어 `autoCommit=false`로 시작하고, 커넥션을 ThreadLocal에 바인딩합니다. 메서드가 정상 종료되면 커밋, RuntimeException이나 Error가 나오면 롤백합니다. Checked 예외는 기본적으로 롤백하지 않습니다.

**Q. 같은 클래스 내부 호출 시 왜 적용이 안 되나요?**
> 트랜잭션 로직은 프록시에 있는데, 내부 호출은 `this`로 진짜 객체를 직접 부르기 때문에 프록시를 거치지 않습니다. 해결은 트랜잭션 메서드를 별도 빈으로 분리해 주입받아 호출하는 것이 가장 깔끔합니다.

**Q. private 메서드에 붙이면?**
> CGLIB 프록시는 서브클래스라 private 메서드를 오버라이드할 수 없어 조용히 무시됩니다. final 메서드도 같습니다. public 메서드에만 붙여야 합니다.

**Q. REQUIRES_NEW와 NESTED의 차이는?**
> REQUIRES_NEW는 커넥션을 새로 잡는 완전히 별개의 물리 트랜잭션이라 먼저 커밋되고, 바깥이 롤백돼도 남습니다. NESTED는 같은 트랜잭션 안의 Savepoint라 내부만 부분 롤백은 되지만, 바깥이 롤백되면 함께 사라집니다. 그리고 NESTED는 JPA에서 지원하지 않습니다.

**Q. REQUIRED 외에 실무에서 뭘 써봤나요?**
> 본 작업 실패 시 실패 이력을 남기기 위해 REQUIRES_NEW를 썼습니다. 이력 서비스를 별도 빈으로 분리해 self-invocation을 피했고, 이력 저장 자체의 예외는 catch해서 원래 실패 원인을 덮지 않게 했습니다. REQUIRES_NEW는 커넥션을 2개 점유하므로 풀 고갈 데드락을 고려해 풀 사이즈를 조정했고, 성공 이력은 먼저 커밋되면 불일치가 생기므로 `@TransactionalEventListener(AFTER_COMMIT)`로 시점을 분리했습니다.
