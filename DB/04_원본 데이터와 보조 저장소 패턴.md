# 원본 데이터와 보조 저장소 패턴 (Source of Truth + Derived Store)
> 왜 회사들은 RDB 하나가 아니라 Redis, ElasticSearch 같은 저장소를 함께 쓰는가?
 
## 1. 핵심 기념
### 원본 데이터 (Source of Truth)
정합성 측면에서 가장 신뢰할 수 있는 기준 데이터, 보통 RDB가 담당 (트랜잭션, 정합성 보장)

### 보조 저장소 (Derived Store)
특정 워크로드(업무/조회 패턴)에 최적화된 파생 저장소, 예 : ElasticSearch, Redis, Vector DB, BigQuery

### 폴리글랏 퍼시스턴스 (Polyglot Persistence)
목적에 맞게 여러 데이터베이스를 함께 사용하는 상위 아키텍처 개념. 이 패턴은 그 구현 형태중 하나

패턴의 본질 : RDB는 강력하지만 특정 워크로드 (대규모 검색, 카운터 폭주, 실시간 랭킹 등)에는
한계가 있다. 원본 저장소가 신뢰의 기준을 지키고, 보조 저장소가 그 한계를 메꾼다.
- 원본 저장소가 반드시 RDB일 필요는 없음 (문서, 이미지도 원본이 될 수 있음)
---
## 2. 실무 사례: 게임 커뮤니티 설계
### 배경
- 수십만 동시 접속자 예상 규모의 모바일 게임, 자체 커뮤니티 개발
- 검색 대상: 6개월 / 12개월 / 전체 누적 게시물 -> 검색 데이터가 무한히 증가
- 요구 검색 기능 : 다중 필드(제목,작성자,내용,태그), 본문 검색, 한국어 형태소 분석, 오타 혀용, 자동 완성

### 선택
- 원본: RDB 유지 : 트랜잭션, 정합성 보장 + 조직의 데이터 거버넌스(OLAP, BI)가 RDB 기반
- 보조 : Elasticsearch : 강력한 검색 기능 + 이벤트 점검 시 트래픽 폭주 대비 + RDB로 부터 검색 부하 분리

### 운영 방식
1. 게시물 등록 시 -> RDB에 저장 + Elasticsearch에 색인
2. 검색 시 -> Elasticsearch에서 게시물 ID 조회 -> RDB에서 인덱스 쿼리로 전체 내용 조회
---

## 3. 2단계 조회 패턴 (먼저 찾고, 다음에 가져온다.)
```
[사용자 검색] -> [보조 저장소] 후보 ID 목록 조회 (워크로드 최적화) 
            -> [원본 저장소] ID 기반 인덱스 쿼리로 전체 데이터 조회
            -> [애플리케이션] 조합/재정렬 후 반환
```
### 왜 2단계로 나누는가?
- 보조 저장소 : 특정 조회 패턴에 최적화 (역색인, Sorted Set 등)
- 원본 데이터 : 트랜잭션 보장, 관계형 조인에 강함
- 각자 잘하는 역할로 분리

예시 1 - 게시판 풀텍스트 검색 : ES의 분석기 + 역색인으로 본문 단어를 빠르게 매칭 -> 게시물
데이터 자체는 원본 RDB에서 조회 (참고 : RDB의 풀텍스트 검색을 지원하지만, 검색이 핵심 기능이거나 대규모일 때 ES가 진가를 발휘)

예시2 - 다중 기준 랭킹 : Redis Sorted Set에 1차 기준 점수로 정렬해 후보를 빠르게 추림 -> 
RDB 또는 Redis Hash에서 보조 정보(시간, 카테고리 가중치) 조회 -> 애플맄이션 최종 순위 재조정

## 4. RDB만으로 부족한 대표 상황

### 본문검색
- Like '%키워드%'는 인덱스를 못타서 풀 테이블 스캔 발생 
- Elasticsearch 사용

### 좋아요 폭주
- 인기글에 행 단위 락 -> 경합 -> 응답 지연, 다른 트랜잭션 영향
- Redis (쓰기 빠름, 싱글스레드 모듈)

### 실시간 랭킹
- 대상이 많아지면 정렬 비용, 특정 순위 조회 부하
- Redis Sorted Set

### 위치기반 검색 ("내 주변 1km")
- RDB로 해결 어려움
- Redis GEO, PostGIS

## 5. 실무 사례 7가지 (모두 같은 구조)

1. 검색 - Elasticsearch - 게시판 본문 검색, 이커머스 상품 검색, 로그 검색
2. 랭킹 - Redis Sorted Set - 게임 리더보드, 가중 기준 랭킹의 1차 저장소
3. 캐시 - Redis(Look-aside/Cache-aside) - 세션, 프로필, 권한, 자주 안변하는 코드 테이블
4. 쓰기 최적화 락 경합 방지 - Redis - 인기 게시물 조회수 좋아요 카운터
5. 위치 기반 검색 - Redis GEO, PostGIS - 내 주변 검색
6. 의미(시멘틱) 검색 - Vector DB (Pinecone, pgvector) - 유사 문서 검색
7. 데이터 분석 - BigQuery, ClickHouse - 운영 DB에 부담 없이 대량 데이터 생산

> 메타 시각 : 도구만 바뀔 뿐 패턴의 원리는 동일하다. 개별 사례를 넘어 사례들을 관통하는 공통 구조를 보는 시각을 가져야 함 

## 6. 핵심 원칙 3가지
1. 재구성 가능성 : 보조 저장소의 데이터는 사라져도 원본 데이터에서 언제든 재구성 가능해야 한다. (가장 중요한 원칙)
2. 단방향 동기화 : 원본 -> 보조 방향으로만 데이터가 흐르는 것이 안전하다.
3. 최종 일관성 (Eventual Consistency) : 보조 저장소는 강한 일관성이 아닌 이상 최종적 일관성을 목표로 한다.
   - 강한 일관성(RDB) : 모든 시점에 데이터가 정확히 일치
   - 최종적 일관성 : 잠시 어긋날 수 있지만 결국 일치 

## 7. 트레이드 오프 - 분리는 공짜가 아니다.

### 듀얼 라이트(Dual Write) 정합성 문제
- RDB 쓰기는 성공했는데 ES는 실패 -> 두 저장소 데이터가 어긋나기 시작 -> 일관성 붕괴
- 해결 : 아웃박스 패턴(Outbox Pattern) 또는 CDC (Change Data Capture)로 별도 설계 필수

### 다중 저장소의 비용
- 운영 비용 증가
- 듀얼 라이트 정합성 문제
- 학습 비용 (팀 전체가 새 도구 습득)
- 인프라 비용 (노드 수 증가, 라이선스)
- 장애 시 디버깅 복잡도 증가

### "Just Use Postgres"
- PostgreSQL 하나로도 : 벡터 검색(pgVector), 위치 기반(PostGIS), 풀텍스트 검색, JSON 문서 저장, 경량 pub/sub 알림, 시계열 확장 기능
- 작은 팀, 초기 트래픽에는 단일 DB가 더 빠른 가치를 만든다.

## 8. 현실적인 아키텍쳐 전략 - 단계별 점진 확장
> 처음부터 모든 도구를 갖추려고 하지 말 것. 병목이 증명될 때 점진적 확장

### MVP/초기
단일 DB + 그 DB의 확장 기능. 트래픽 작고 패턴 한정적 -> 운영의 단순함이 최우선

### 성장기
특정 조회 부하가 누적되면 Redis 도입 (트래픽 부하 큰 서비스에서 가장 먼저 추가되는 도구)

### 확장기
검색을 전문 검색 엔진으로 분리, 분석 도구 도입, 병목이 발생하거나 명백히 필요한 영역만 최적화

### 대규모
본격적인 폴리글랏 아키텍처, N개 저장소가 동일한 데이터 기반이 되도록 아웃박스 패턴 / CDC로 일관성 유지


## 9. 한줄 요약
- 원본(RDB)의 장점은 유지하면서, 특화 워크로드는 보조 저장소로 보완하는 패턴
- 검색·랭킹·캐시·카운터·위치·벡터 검색 — 모두 같은 원리의 변형
- 분리는 공짜가 아니다 → 단일 DB로 시작, 병목 증명 후 점진 확장
- 보조 저장소는 원본에서 재구성 가능하게, 듀얼 라이트 정합성은 반드시 별도 설계
- 아키텍처 역량 = 도구를 많이 아는 것이 아니라, 적절한 도구를 선택하는 안목

## 셀프 체크 질문
- LIKE '%키워드%' 검색이 느린 근본 원인은? (인덱스를 타지 못해 풀 테이블 스캔 발생)
- 좋아요 카운터에 Redis를 쓰는 이유 두 가지는? (빠른 쓰기, 행 락 경합 회피)
- 2단계 조회 패턴에서 각 단계가 담당하는 것은? (보조: 후보 ID 추출 / 원본: 전체 데이터 조회)
- 보조 저장소 설계의 제1원칙은? (원본으로부터 재구성 가능해야 함)
- 듀얼 라이트 문제란 무엇이고 해결책은? (한쪽 쓰기만 성공해 정합성 깨짐 → 아웃박스 패턴 / CDC)
- 처음부터 다중 저장소로 시작하면 안 되는 이유는? (운영·학습·인프라 비용, 디버깅 복잡도 — 병목 증명 후 확장)
